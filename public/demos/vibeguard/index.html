클라이언트가 실제로 체감할 수 있는 위험 기준으로 정리했습니다. 각 항목 아래에는 수정이 먹혔는지 확인한 검증 결과가 붙습니다.

01

사용자가 관리자라고 속일 수 있는 권한 구조

AUTHZ
BEFORE · 위험클라이언트가 보낸 역할 값을 신뢰

브라우저 요청에서 관리자 역할을 주장하면 서버 로직이 그 값을 믿을 여지가 있었습니다.

x-role: admin → 관리자 기능 판단에 사용
→
AFTER · 수정로그인 사용자와 DB 권한을 서버가 직접 확인

auth.uid()로 실제 사용자를 식별하고 DB의 role을 기준으로 관리자 RPC 접근을 제한했습니다. 일반 사용자의 자기 role 변경도 DB trigger로 막았습니다.

auth.uid() → profiles.role 확인 → admin만 관리자 RPC 허용
검증일반 사용자의 관리자 export 호출 거부 · 자기 계정 role을 admin으로 변경하는 시도 거부
02

다른 사용자의 프로필·파일에 접근할 수 있는 경계

RLS / STORAGE
BEFORE · 위험“로그인했다”와 “이 데이터를 볼 권한이 있다”가 분리되지 않음

AI 코딩 앱에서 흔한 형태처럼, 인증만 되어 있으면 타 사용자 데이터나 저장 경로까지 권한 경계가 느슨해질 수 있었습니다.

→
AFTER · 수정사용자별 RLS + Storage owner path 적용

프로필은 본인 또는 관리자만 접근하도록 RLS를 다시 설계하고, 파일 저장도 로그인 사용자 자신의 경로에만 쓰도록 제한했습니다.

user A → profile A : 허용 user A → profile B : 차단 user A → storage/B/* : 차단
검증A 사용자가 B 프로필 조회/수정 실패 · 타 사용자 Storage 경로 write 실패 · 관리자 접근은 정상 동작
03

연타·재시도·동시 요청으로 투표가 여러 번 들어가는 문제

DATA INTEGRITY
BEFORE · 위험투표 저장과 카운트 증가가 따로 움직임

버튼 연타, 네트워크 재시도, 여러 탭에서 동시에 요청하면 같은 사용자의 투표가 중복 반영될 가능성이 있었습니다.

INSERT vote UPDATE count +1 INSERT event 각각 별도 실행
→
AFTER · 수정직접 INSERT 금지 + DB UNIQUE + 단일 RPC 트랜잭션

submit_vote() 안에서 투표 행·집계·canonical 이벤트를 한 번에 처리하고, UNIQUE(poll_id,user_id)로 DB 자체가 중복을 거부합니다.

submit_vote() → vote 1건 → count +1 → vote_submitted 1건 모두 한 트랜잭션
검증같은 사용자의 논리적 투표를 20개 DB 세션에서 동시에 요청 → 최종 vote row 1 · aggregate 1 · vote_submitted event 1
04

사용자가 분석 이벤트를 직접 조작할 수 있는 문제

EVENT INTEGRITY
BEFORE · 위험클라이언트가 중요한 이벤트를 직접 기록 가능

예를 들어 실제 투표를 하지 않고도 vote_submitted 이벤트만 만들어 분석 수치를 부풀릴 수 있는 구조는 신뢰할 수 없습니다.

→
AFTER · 수정일반 이벤트와 canonical 이벤트 경로 분리

직접 user_events INSERT를 막고, 일반 행동은 allowlist가 있는 record_event()로만 기록합니다. vote_submitted는 오직 실제 투표 RPC 안에서만 생성됩니다.

record_event("content_viewed") ✓ record_event("vote_submitted") ✕ submit_vote() → vote_submitted ✓
검증정상 content_viewed 기록 성공 · 위조 vote_submitted 요청 실패 · 직접 user_events INSERT 실패
05

“내 PC에서는 됨” 수준의 배포 검증

STABILITY
BEFORE · 부족브라우저 회귀·서버 상태·사용자 이탈을 확인할 근거가 부족

기능 구현만으로는 iPhone 계열 엔진, 모바일 Chrome, 서버 readiness, 퍼널 이탈 여부를 알 수 없습니다.

→
AFTER · 수정Release gate + health/readiness + 실제 퍼널 이벤트 추가

Chromium·WebKit·Android형 Chromium E2E, console/page error 검사, health/readiness API, 사용자 행동 퍼널과 관리자 CSV export를 붙였습니다.

content_viewed → vote_started → result_viewed + health / readiness + 3 browser projects
검증3개 브라우저 프로젝트 E2E PASS · 핵심 흐름 console/page error 0 · 퍼널 이벤트 발생 순서 확인

수정 후 핵심 요청 흐름

중요한 변경은 “프론트에서 DB를 믿고 직접 건드리는 구조”를 “검증된 서버/DB 함수만 통과하는 구조”로 바꾼 것입니다.
